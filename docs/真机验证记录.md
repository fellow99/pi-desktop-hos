## 关键发现（含对规划文档的修正）

### 发现 1 — Next 的进程内服务器入口已确认 ✅（规划 §11.2 O1 关闭）

`next/dist/server/lib/start-server.js` 的导出可直接在进程内调用，**宿主不退出**。
门禁实测：`start-server:node_modules\next\dist\server\lib\start-server.js（1786 ms）`。

工程规划 §4.2 的「候选 A」成立，**未落到候选 B（子进程）**，因此三个平台级子进程问题
（exit 事件不观测 / 僵尸泄漏 / 应用域 JIT 被拦）全部规避。

### 发现 2 — Node 22.17.0 足以运行 pi 1.1.0 + Next 16.3.8 ✅（规划 §11.1 R2 关闭）

上游声明 `>=22.19.0`，设备运行时是 **22.17.0**（差 2 个 patch）。用官方 22.17.0 二进制实测：
服务端启动、`GET /` 200、`/api/web-auth` 200、Host 围栏放行局域网 IP、鉴权启用、对 `pi-dist`
部署物的完整冒烟 —— 全部通过。**无需为 Node 版本写补丁，也无需升 Electron 40。**

### 发现 3 — ⚠️ 构建用 node 必须显式指定，不能靠改 PATH

系统 PATH 上是 Node 24，DevEco 自带的是 Node 18（上游依赖要求 ≥20）。
**Git Bash 里 `export PATH=<node22dir>:$PATH` 实测无效** —— `command -v node` 仍指向系统 node
（Windows PATH 排序压过 Bash 的 PATH）。因此 `prepare-next.mjs` 增加 `--node <path>` 开关。

更关键：**`npm ci` 与 `next build` 必须用同一个 node 跑**。实测用 Node 18 装依赖时
`@tailwindcss/oxide` 的 optionalDependencies 平台解析没装全，随后用 Node 24 构建报
`Cannot find native binding`。两处都必须走同一 `NODE_BIN`。

### 发现 4 — ⚠️ 裁剪原生件的**位置**错了会引发联网补下载（已修正）

初版在 `prepare-next.mjs` 里删除 `pi-web/node_modules` 下所有非 arm64 的 `*.node`。
实测两个后果：

1. 删掉 `@next/swc-win32-x64-msvc` 后，`next start` 首次运行打印
   `Downloading swc package @next/swc-win32-x64-msvc... `，从 registry 拉 **34 MB** 到
   `%LOCALAPPDATA%\next-swc`，就绪时间从 **1.5 s → 5.8 s**。设备**离线**，这条下载会失败/超时。
2. 下一次 `next build` 会把 `@img/sharp-*`、`@tailwindcss/oxide-*`、`@unrs/resolver-binding-*`、
   `lightningcss-*` 四个包**原样装回** —— 对源目录的删除本就是无效的。

**修正**：`prepare-next` 阶段 3 改为**只统计不删除**；真正的裁剪移到 `collect-pi.mjs`，
在**复制后的 `pi-dist/node_modules` 副本**上做（源目录保持完整）。

### 发现 5 — ✅ SWC 的 aarch64-ohos 缺口用 **WASM 版 SWC** 彻底解决（规划新增知识）
> ⚠️ **本发现的「落点依据」在轮次 1 被真机推翻**（正确落点见「轮次 1 · 发现 10」）：内置位置必须是 `node_modules/next/wasm/@next/swc-wasm-nodejs/`。下面那段推理与「零下载」对照表保留原样以便追溯，但其结论**不成立** —— 当时宿主机上遗留了一个已解压目录，掩盖了真实加载路径。


**问题**：Next 运行期用 SWC 编译 `next.config.ts`。缺原生绑定时它的回退顺序是
`next-swc-fallback/<当前平台>` → `@next/swc-wasm-nodejs` → **联网补下载**。
而 npm 上 `@next/swc` 只有两种 linux-arm64 变体：

| 包 | registry 是否存在 |
|---|---|
| `@next/swc-linux-arm64-ohos` | ❌ **不存在** |
| `@next/swc-linux-arm64-musl` | ✅ 存在（16.4.0） |
| `@next/swc-linux-arm64-gnu` | ✅ 存在（16.4.0） |

即**没有 ohos 目标**，而 `linux-arm64-musl` 能否在 ohos 上加载未验证（ABI 风险）。

**解法（✅ 实测）**：内置平台无关的 WASM 版 SWC。
`collect-pi.mjs` 的 `provisionWasmSwc()` 从 registry 取
`@next/swc-wasm-nodejs@<next 版本>`（16.3.8，解压 29 MB）放进
`pi-dist/node_modules/@next/swc-wasm-nodejs/`。

**落点依据**（读自 Next 源码 `dist/build/swc/index.js` 的 `loadWasmRawBindings`）：
`importPath` 为空时按**裸包名**解析，即 `node_modules/@next/swc-wasm-nodejs/wasm.js`。

**实测对照**（每次都清空 `%LOCALAPPDATA%\next-swc`）：

| 配置 | `next.config.ts` | 是否联网下载 | 缓存目录 |
|---|---|---|---|
| 只有 win32 原生件 | 1635 ms | ✅ 下载 WASM 包 | 被创建 |
| **内置 WASM SWC** | **276 ms** | **❌ 零下载** | **未创建** |

门禁 9 PASS / 0 FAIL；`DEBUG=*` 日志显示 `next-swc build: wasm build @next/swc-wasm-nodejs`
—— 命中的正是内置包。

WASM 是**平台无关**的：同一份字节在 aarch64-ohos 上同样可用，**不需要交叉编译**。
这比交叉编译原生 SWC（或复刻上游的 Rust 编译器）要务实得多。

### 发现 6 — ⚠️ 鸿蒙资源目录禁止非 ASCII 文件名

第一次构建在第 26 s 失败：

```
ERROR: Failed :electron:default@CompileResource
Error Code: 11211116   Resource Pack Error
Invalid resource name 'README-媒体资源'. It should match the pattern [a-zA-Z0-9_].
```

原因是我在 `AppScope/resources/base/media/` 放了一份中文名的说明文件。
**规则**：`resources/` 下只能放资源本体，且文件名必须匹配 `[a-zA-Z0-9_]`。
该说明已移到 `docs/media-placeholder-icons.md`。

### 发现 7 — ⚠️ Git-Bash 的 `tar` 拒收盘符路径

`tar -czf D:\x\y.tar.gz …` 与 `tar -czf D:/x/y.tar.gz …` **都**报
`tar (child): Cannot connect to D: resolve failed` —— 它把盘符当成**远程主机**。
修法：用**相对路径**（`cwd` 指到工程根，归档名与源都用相对名）。
`collect-runtime.mjs` 的阶段 0b 因此改用 Python `tarfile`（同时获得「不覆盖已有文件」的语义）。

### 发现 8 — ⚠️ Windows 下 `shell: true` 必须给参数加引号

`prepare-next.mjs` 原本用 `execFileSync(cmd, args, { shell: true })` 以便解析 `npm.cmd`。
但 `shell: true` 会把参数交给 cmd.exe 再解析一次，**含空格的路径必须显式加引号**。
实测触发：DevEco 的 node 在 `D:\oh-workspace\DevEco Studio\tools\node\`，路径里的空格被拆成两段
（`'D:\oh-workspace\DevEco' 不是内部或外部命令`）。修法：按 cmd.exe 规则给每个参数加引号。

### 发现 9 — 门禁的 SSE 项在无会话时无法断言（SKIP，非失败）

`GET /api/agent/<id>/events` 对未知 id 返回 **404**，因此没有真实会话 id 时无法断言
`text/event-stream`。门禁按设计记为 SKIP。**上真机后必须在真机复验该项。**

（此后 10+ 分钟既无成功也无失败日志；页面永久停在启动闪屏；进程存活但无任何进展）

**根因**（读自 `next/dist/build/swc/index.js` 的 `tryLoadWasmWithFallback`）：

1. `loadWasm('')` 里是 `import(pathToFileURL(pkgPath))` —— **即使 `importPath` 为空也先 `pathToFileURL`**，于是裸包名被解析成 `<cwd>/@next/swc-wasm-nodejs` 这种不存在的路径 → **必失败**。v1.1 把 WASM 放在 `node_modules/@next/swc-wasm-nodejs`，恰好落在这条**死路**上。
2. 回退到 `downloadWasmSwc(nextVersion, wasmDirectory)`，其中 `wasmDirectory = join(dirname(require.resolve('next/package.json')), 'wasm')`，即 `node_modules/next/wasm/`。该函数**先判 `node_modules/next/wasm/@next/swc-wasm-nodejs/` 是否存在，存在就直接 return**（既不联网、也不读 npm 缓存）；随后 `loadWasm(wasmDirectory)` 以**绝对路径** import 该目录下的 `wasm.js`。

**为什么轮次 0 会得出相反结论**：宿主机上更早的一次真实联网下载把 `node_modules/next/wasm/@next/swc-wasm-nodejs/` **留在了产物副本里**（该目录时间 16:20:36，**晚于** tar 的 16:20:28 —— 即它根本没进归档），使后续测量命中了「提前返回」；而真机全新安装没有这个遗留目录，于是现出原形。

### 发现 11 — ⛔ 子进程 `exit`/`close` 永不送达 → pi 的 `bash` 工具真机不可用（新增 R14）

用最小探针（CDP → 主进程）逐层定位：

| 探针 | 结果 |
|---|---|
| `spawnSync('/bin/sh', ['-c','echo …'])` | **整个主进程挂死**：CDP 20 s 无响应、`Runtime.evaluate` 永不返回；进程保持 `S` 态、CPU 时间不再增长；随后被系统清理（`ps`、`aa dump` 均查不到） |
| `spawn('/bin/sh', ['-c','echo async-ok; id'])`（异步，正是 pi 的用法） | **命令确实执行**：stdout = `async-ok` + `uid=20020213(pci) gid=20020213(pci_a20213) … context=u:r:debug_hap:s0`；但 8 s 内 **`exit` 未触发** |
| 终局判定（12.5 s 采样） | 子进程 **1.5 s 内即变僵尸**（`/proc/<pid>/stat` 状态字段 = `Z`）并维持到 12.5 s；`exit`/`close`/`error` **事件数组始终为空** |

**影响**：pi 的 `bash` 工具用 `waitForChildProcess(child)` 等 `exit`/`close` 判定结束 → **在设备上会一直挂**；且**每次 spawn 泄漏 1 个僵尸**（与 dsh 记录的「exit 不触发 + 每 spawn 泄漏僵尸」一致）。主机侧「进程内宿主、不起子进程」的设计规避了宿主自身的问题，但**用户的 shell 工具仍走 spawn** → 本工程的功能缺口（**非上架阻塞**）。处置见工程规划 R14（首选壳扩展替换工具，零上游补丁）。

### 发现 12 — 视觉取证的坑：`snapshot_display` 拍不到 Electron 的 GPU 合成面

`snapshot_display -f …jpeg` 能成功出图（3120×2080），但窗口区域 **99.3% 为纯白**（暗于 200 的像素仅 0.54%），**极易误判成「白屏故障」**。证明不是白屏的两条独立证据：

1. **DOM 探针**：`readyState=complete` + 完整中文 UI 文本（见上表）；
2. **`webContents.capturePage()`**（渲染进程自身截图，2280×1532）经 **min-pooling** 渲染后可见侧边栏分隔线、正文段落块、底栏三项 —— UI 确实画出来了。

### 发现 13 — hdc 侧的两个坑

1. **`fport` 转发的生命周期**：`hdc fport tcp:19229 tcp:9229` 建立后，**该 hdc 客户端一退出映射即失效**（`fport ls` 显示 `[Empty]`，随后 curl 报 `ECONNREFUSED`）。因此「建转发 + 消费转发」必须在**同一次命令**内完成。
2. **偶发 `need connect-key`**：`fport`、`app uninstall`、`aa force-stop` 有时报 `[Fail]ExecuteCommand need connect-key? please confirm a device by help info`（有时即使已给 `-t` 也一样，重试即可）。稳妥写法：设备命令一律带 `-t <connectkey>`，外层做重试。

### 发现 14 — Git-Bash 会改写传给设备的 POSIX 路径参数

本机 Git-Bash 把命令行参数 `/bin/sh` 改写成 `C:/Program Files/Git/usr/bin/sh`（MSYS 路径转换），设备侧于是收到一个不存在的路径、探针报 `ENOENT` —— 足以**误导结论**。凡把 `/bin/…`、`/data/…` 这类**设备侧路径**当参数传下去，必须 `MSYS_NO_PATHCONV=1`。

### 发现 18 — ⛔ `/system/bin` 批量探测的 `reboot` 回弹（跨设备复现，本轮把设备重启了）

对照参考清单枚举 `/system/bin` 时，一个**第三方脚本**以「**裸名** + `--help`」模式逐个探测。
`/system/bin/reboot` 是指向 **`begetctl`** 的软链，`--help` 被 `begetctl` 当作重启命令执行 →
**设备于 ~15:09 重启**（`uptime` 归零）。本工程自己的脚本用 `toybox <n> --help`，而 **`reboot` 不在
裸 `toybox` 的小程序表内** → `toybox: Unknown command reboot`（安全）。→ **硬约束：任何批量探测
`/system/bin` 的脚本，只允许对 `toybox <n>` 传参，且先确认 `<n>` 在小程序表内。**

### 发现 19 — ⚠️ toybox 枚举的两处方法学修正

1. **不能用 `toybox <n> --help` 判「可派发」**：`grep`/`diff`/`env`/`sort`/`cmp`/`chroot`/`timeout`/`false`
   等小程序**不接受** `--help`（返回非零），会被误判成「悬空软链」。判据须改为
   **「该名是否在裸 `toybox` 输出的小程序表内」**。用错判据时 A 类会从 177 掉到 166。
2. **不能用 `[ -L ]` 判是否软链**：shell 域对**单条目** `lstat` 被拒
   （`ls -l /system/bin/cat` → `Permission denied`），`[ -L ]` **恒假**，会把 230 个软链全判成普通文件。
   可靠做法是 **`ls -l /system/bin` 目录列表**（可读）+ **`readlink`**（可读）。

→ 用修正后的判据，枚举结果与参考工程**同构且同数**：编译 **178** / A 类 **177**（166 裸名 + 11 mksh 遮蔽）/
B 类 **1**（`nc`）/ 悬空 **42** / 非 toybox 软链 ≥5（`reboot`·`service_control`→`begetctl`，
`f2fslabel`·`resize.f2fs`·`sload.f2fs`→`fsck.f2fs`）/ mksh 遮蔽 **11** / 恒等 alias **139**。

### 发现 23 — ⚠️ `/data/service/hnp` 的跨域可见性：shell 域报 `ENOENT`（不是「不存在」）

应用域 `statSync('/data/service/hnp/bin/node')` → **存在，116,927,320 B**；
而 **shell 域**：`ls -ld /data/service/hnp` → **`No such file or directory`（ENOENT）**、
`ls -l /data/service` → `Permission denied`、`ls -ld /data/storage/el2/base/files` → `Permission denied`。
→ 复现参考工程的「陷阱」，且本轮取到了**确切 errno**：`ENOENT` 是 SELinux 域隔离的**伪装**，
**不等于路径不存在**。⚠️ 注意区分两件事：shell 域的 `command -v node` = absent **只**证明「不在 PATH」，
**不能**证明「不可见」——本文已按实测数据把这两件事分开陈述。
→ **任何关于 HNP / 系统挂载点的结论必须从应用域取证。**
