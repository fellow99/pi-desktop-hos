# skills/ — 壳专用技能

本目录存放 **Pi Desktop 壳专用**的 pi 技能（`SKILL.md`）。构建期由 `scripts/collect-pi.mjs`
打进 `pi-dist/resources/pi-agent/skills/`；运行期由 `src-main/main.js` 的产物解压引导
把它们 **copy 物化**（**禁用 symlink**）到

```
<userData>/pi-agent/skills/
```

pi 会自动发现该目录（`skills` 是内建的技能发现集之一），因此无需在 `settings.json`
里声明路径。

## 目录内容

| 技能 | 作用 |
|---|---|
| `harmony-runtime-capabilities/SKILL.md` | 描述**本构建的能力边界**：哪些内建工具可用、为什么 `find`/`grep` 不可用以及用什么替代、`bash` 实际 spawn 的是什么、为什么子进程跑不了 Node、哪些文件操作行为不同。 |

## 技能格式（pi 的契约，不是我们自造的）

- 顶层目录 `<name>/SKILL.md`，或顶层单文件 `<name>.md`。**嵌套的 `**/SKILL.md` 不会被发现。**
- frontmatter 必填 `name` + `description`；可选 `whenToUse` / `metadata` /
  `disable-model-invocation` / `user-invocable`。**驼峰旧键会被拒。**
- **技能名不加前缀。** 技能名是模型可见的标识符，也是用户手敲的 `/name`，归属由**目录**
  表达而不是由名字表达。（这与参考工程 `dsh-desktop-hos` 的结论一致，而对扩展则相反 ——
  扩展是代码，命名空间冲突的代价更高。）
- 加载是**惰性的**：进程启动只登记技能目录（名称 + 截断的 description），技能正文按需
  加载（`skill` 工具或人工 `/name`）。

## ⚠️ 维护纪律：能力变化时必须同步更新技能

**过期技能比没有技能更有害。** 参考工程有过一次实证教训：`delete`/`move` 能力交付之后，
描述能力边界的技能仍声称它们不存在，导致模型**拒绝使用已经交付的工具** —— 能力明明在，
却被自己发的文档挡在门外。

因此：

- 本技能的正文描述的是**本构建的能力边界**。任何能力的状态变化（新增、删除、降级、
  升级恢复）都必须**同一次改动内**更新 `harmony-runtime-capabilities/SKILL.md`。
- 判据（沿用 oc-desktop-hos 的纪律）：**先改规范源，再改技能；不允许出现「技能有、规范源无」的结论。**
  本工程的规范源是 `docs/工程规划.md` 的 **§9.3（能力缺口与降级表）** 与 **§11（风险与开放问题）**。
- 技能里引用文档时用 **§ 号**而不是行号（行号会随编辑漂移）。
- 不要把未实测的结论写成事实。本工程采用四种证据标记（`docs/工程规划.md` §0.2）：
  ✅ 实测 / 🔶 沿用 / ⬜ 待验证 / ⚠️ 冲突。技能正文面向模型，应当只陈述**已确定**的事实；
  未实测项要么不写，要么明确标注为未验证。
