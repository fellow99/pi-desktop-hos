### 0.3 非目标（本版明确不做）

- **不 fork `pi` / `pi-web`**：对上游只做幂等补丁（本版预计 0 条，见 §7）。
- **不规划「随包分发并执行自有 ELF」**：该路线已被同型工程真机封死（🔶 需 AGC 二进制证书 `certType: 4`，个人开发者不可得）。本工程不需要它 —— Electron 自带 Node 22.17 就是运行时。
- **不做鸿蒙手机（`phone`）适配**：目标设备仅 `2in1` 与 `tablet`（对齐运行时）。
- **不做 macOS / Linux / Windows 桌面壳**：`pi` 自带 CLI/TUI，`pi-web` 自带浏览器形态，本工程不重复建设。
- **v1 不做主 UI 的 ArkWeb 迁移**（见 §4.7，已决策为触发式目标）。
- **不做自动更新**（🔶 鸿蒙只有 `updateManager` 的「发现新版本 + 跳转 AppGallery」，无静默自更新公开 API）。

## 1. 项目概述

### 1.1 一句话定义

把 [Pi](https://pi.dev)（可扩展的 agent harness）与其浏览器界面 [Pi Web](https://github.com/agegr/pi-web) 封装成鸿蒙 PC / OpenHarmony 桌面的一等公民桌面应用：用 `harmonypc-electron` 提供的 Electron-on-鸿蒙运行时承载 **pi-web 的 Next.js 服务端（含 agent 与 `/api`）**，渲染层同源加载该服务端提供的 Pi Web UI，最终打包为可签名分发的 HAP。

**应用名 / 包名**：**`Pi Desktop`** / **`org.fellow99.pi.PiDesktop`**（⬜ 主体与包名的注册归属需人工确认，见 §12）。

## 2. 背景

### 2.1 `pi`（宿主）

- **是什么**：`pi` 是「最小、可扩展的 agent harness」—— 把 agent harness 做成可被改造成任何形态的骨架：扩展、技能、提示模板、主题均可替换，官方另有 CLI、RPC、JSON、SDK 四种集成入口。
- **包结构**（monorepo，`pi/packages/`）：`agent`（agent 运行时）、`ai`（多 provider LLM API）、`coding-agent`（CLI + SDK + 扩展系统，**本工程的核心依赖**）、`tui`（终端 UI 库）、`durable`、`chord`、`server`、`mcp`、`protocol`、`telemetry`、`env`、`evals`、`client`、`codemode`。
- **运行形态**（`packages/coding-agent/docs/cli.md`）：交互式 TUI、`--print`、`--mode json`、`--mode rpc`（JSONL over stdin/stdout）、以及**进程内 TypeScript SDK**。
- **关键事实 A**：`pi` **没有 HTTP 服务模式**。`packages/server` 是实验性的 Unix socket 路由层（`docs`/README 自述 experimental，且只是 `coding-agent` 的 devDependency），不是给外部消费的 HTTP 服务。
- **关键事实 B**：`pi` 的扩展系统是**进程内 jiti 加载的 TS/JS 模块**，无需编译、无独立进程。

### 2.2 `pi-web`（UI + 服务端）

- **是什么**：`pi` 的本地浏览器 UI，Next.js **16.3.8** App Router 应用。
- **形态（本工程的关键前提）**：**一个 Node 进程同时提供 SPA 与 `/api/*`**。
  - 启动：`pi-web`（bin）→ `spawn(process.execPath, [next, "start", "-p", port, "-H", host])`，等待子进程 stdout 出现 `Ready`。
  - 产物：npm tarball 的 `files` 含 **`.next`**（生产构建产物随之分发）。
- **agent 在进程内**：`lib/rpc-manager.ts` 直接 `import` `@earendil-works/pi-coding-agent` 的 `createAgentSessionFromServices` / `createAgentSessionServices` / `SessionManager` 等 —— **不需要 `pi` 二进制在 PATH 上，也不需要 spawn `pi`**（`next.config.ts` 的 `serverExternalPackages` 明确列出这四个包）。
- **数据面**：HTTP 上行 + **SSE 下行**（`GET /api/agent/[id]/events` → `text/event-stream`）。**没有 WebSocket**。
- **数据位置**：`~/.pi/agent/`（会话 `sessions/<encoded-cwd>/<timestamp>_<uuid>.jsonl`、配置、凭据、扩展、技能），可经 `PI_CODING_AGENT_DIR` 重定向。
- **API 规模**：约 90 条路由（完整清单见 `pi-web/AGENTS.md` 的 File Map）：`sessions/**`、`agent/**`、`files/**`、`git/**`、`worktrees`、`terminal/**`、`auth/**`、`models/**`、`models-config/**`、`mcp/**`、`plugins/**`、`skills/**`、`subagents/**`、`cwd/**`、`project-trust`、`web-auth`、`push/**` 等。

### 2.3 `harmonypc-electron`（运行时）

- **是什么**：Electron 在鸿蒙 PC 上的移植**外壳（shell）基线与样例应用** —— ArkTS 模块（`electron` entry + `web_engine` HAR）+ 预编译闭源 `libelectron.so`。**不是可自举构建的 Electron 源码。**
- **契约清单** `ohos_hap/runtime-manifest.json`：`shellVersion = rc.7-fellow99.baseline.1`、`binaryVersion = v37.2.3-20260825.1`、三个 SO 的 md5、`shellMarkers`、`barrelFile = web_engine/Index.ets`、`bundleNameRewrite.adapters`、`libcxx`。
- **应用代码投放点**：`web_engine/src/main/resources/resfile/resources/app/`（**只读打包**，仅支持 `package.json` 的 `main` 入口；**不支持 asar**）。
- **进程模型**：ArkTS 应用进程内 `import adapter from 'libadapter.so'` → `getNativeContext(contextType)` → `runBrowser(vec_args)` 启动平台主循环；每个 Electron 窗口 = 一个 ArkTS UIAbility；渲染/GPU/crashpad 走 `childProcessManager.startArkChildProcess`（**不是 fork/exec**），默认带 `--no-zygote`。
- **启动参数**（`CommandLineAdapter.ets`）：`--use-gl=egl --enable-features=UseOzonePlatform --ozone-platform=ohos --enable-logging ... --no-zygote --user-data-dir=<沙箱> --inspect`。⚠️ **默认开 `--inspect`，生产构建必须移除**。
- **原生 Node addon**：仅 `arm64-v8a`（`aarch64-linux-ohos`，musl），必须用配套 headers + `libshim.a` 重编；`.node` 放 `electron/libs/arm64-v8a/`，JS 依赖放 `resfile/resources/app/`。
- ⚠️ **仓库不携带运行时二进制**：`electron/libs/` 被 gitignore、`lib.unstripped/*.so` 是 Git-LFS 指针（目标 1,144,209,272 B / 12,522,024 B）。必须从 `harmonypc-electron-versions/v37.2.3-20260825.1-release.zip`（内为 `libelectron_138.tar.gz`，373,947,329 B）解压补齐，且**整套版本严格匹配**；`libc++_shared.so` 取自 DevEco SDK 的 `native/llvm/lib/aarch64-linux-ohos/`。
- ⚠️ **README 徽章写 Electron 34，与 `runtime-manifest.json` 要求的 v37 矛盾** → **以发行版归档产物为准**（v37.2.3 / Node 22.17.0 / ABI 138）。⚠️ 本仓库**未记录**任何鸿蒙沙箱结论（loopback、symlink、HOME、崩溃）—— 这些全部来自 §2.4 的参考工程真机实测。

### 2.4 `dsh-desktop-hos`（骨架与规范镜像源 + 平台事实来源）

本工程**直接复用**其工程框架、构建流水线形态、补丁纪律与 overlay 机制，并把它的鸿蒙真机结论当作 `🔶 沿用` 的输入（不与本工程实测混淆）。

**a) 工程框架（镜像对象）**

| 目录 | 职责 |
|---|---|
| `AppScope/` | 应用级配置（bundleName、版本、图标、label） |
| `electron/` | entry 模块 —— 运行时原生 SO + Chromium 资源 + Ability 装配 |
| `web_engine/` | HAR —— ArkTS 桥接层 + `resfile` 承载应用产物 |
| `src-main/` | Electron 主进程源码（`main.js`、`tar-extract.js`、…） |
| `scripts/` | 构建流水线（`collect-runtime` / `build-*` / `collect-*` + `build-{hap,debug,release}.ps1`） |
| `runtime-overlays/` | 「copy 后回盖」白名单定制保护（prune + overlay + md5 守卫） |
| `patches/<上游tag>/` | 对上游的幂等补丁（按上游 tag 分目录） |
| `plugins/`、`skills/` | 壳专用插件与技能 |
| `specs/`、`docs/` | `NNN-name/{spec.md,plan.md}` 规范体系 + `docs/` 文档集 |
| `hvigor/`、`build-profile.json5`、`hvigorfile.ts`、`oh-package.json5`、`code-linter.json5`、`signing.*.sample` | 构建与签名骨架 |

**b) 鸿蒙平台事实（🔶 沿用，全部来自 dsh 真机实测：`3QC0226526001227` / HarmonyOS 6.1.0.135 / API 24）**

| 能力 | 状态 | 根因层 | 关键证据 / 影响 |
|---|---|---|---|
| loopback（渲染进程访问 `127.0.0.1`） | ❌ | **L1** | 进程间网络隔离拦截 → **必须绑 `0.0.0.0` + 局域网 IP 加载** |
| `fork` + `execve` + PATH 查找 | ✅ | — | 放行；可直接 spawn `/system/bin/sh`（mksh R59）、`/system/bin/toybox`（178 applet） |
| 应用域 fork+exec 出的 node 脚本 | ❌ | **L1 seccomp** | `node -e …` / `node x.js` → **Signal 31（SIGSYS）**；`node -v` 正常 → 子进程**无法分配 JIT 可执行内存** |
| 子进程退出可观测性 | ❌ | **L1** | 事件序列永无 `proc:exit`/`proc:close`；`/proc/<pid>/stat` = `Z`；`cp.exec` 永不回调 → **每 spawn 泄漏 1 僵尸** |
| PTY / 终端 | ❌ | **L1** | SELinux 拒 `forkpty`/`openpty`/`posix_openpt`/`popen`（`EACCES`）；无官方应用级 API |
| symlink（应用域） | ❌ | **L1** | `EACCES`（错误码 `13900012`）；**shell 域 `ln -s` 成功** → 禁令只作用于应用域 |
| hardlink | ❌ | **L1** | hmdfs 无 `.link` 处理器 → `EPERM` |
| `chmod` | ⚠️ 静默失效 | **L1** | hmdfs 不报错但不落实（请求 600/644/640 恒回读 660，755 回读 770）→ **必须写入后回读校验** |
| `homedir()` | ⚠️ | **L1** | 返回沙箱外 `/storage/Users/currentUser`，应用无权限 → **必须把 `HOME` 指向沙箱** |
| `/tmp`、`os.tmpdir()` | ❌ | **L1** | 不可写，且 `TMPDIR` 环境变量对 Node 无效 → 需 monkey-patch |
| 用户目录 `Desktop`/`Documents`/`Download` | ⚠️ | **L1** | 目录 `mode 2771`、属主 `file_manager` → 应用落 "other"；需用户在系统设置授权并**重启应用** |
| 自有 ELF / 自带运行时 | ❌ | **L1（资质）** | 需 AGC 二进制证书 `certType: 4`，**个人开发者不可得** |
| `worker_threads` | ✅ | — | 进程内可用，无需证书/权限，`process.exit` 只退 worker |
| 托盘 / 状态栏 | ✅ 仅 2in1 | — | `statusBarManager` + `StatusBarViewExtensionAbility`，无运行时权限 |
| 后台常驻 / 开机自启 | ⚠️ / ❌ | — / **L1** | 2in1 **最小化不构成后台**（`onBackground` 不触发）；`autoStartupManager` 无公开 setter |
| 无可见窗口常驻 | ✅ | — | `ProcessMode.ATTACH_TO_STATUS_BAR_ITEM` + `StartupVisibility.STARTUP_HIDE`（API 12+） |
| Node ↔ ArkTS 通用桥 | ✅ | — | `systemPreferences.callArkTSFunction` / `callArkTSAsyncFunction`；≤3 参、仅原始类型与数组；**async 方法必须用 async 入口**，否则永久阻塞主进程 |
| `ALLOW_WRITABLE_CODE_MEMORY` | 必需 | **受限权限** | JIT 必需；`system_basic` / since API 14 / 仅平板+2in1 / **须经 AGC 申请 ACL** |

**c) 上架合规硬约束（来自 dsh 的 0.1.5 审核驳回）**

- **N1（P0）**：审核原文「经检测发现，应用渲染打开网页时，未使用 ArkWeb 组件，不符合应用市场审核标准。」→ 该项是本工程选择 R1 通道时**必须登记的最高风险**，见 §4.7 与 §11.1 R1。
- **另一半（低成本可修）**：`EntryAbility.skills` 同时声明 `entity.system.home` + `entity.system.browsable` + `ohos.want.action.viewData` 会被系统当作「可处理 URL 的目标」，强化「浏览器」判定。**移除成本接近零，本工程 Phase 0 就做**。
- 其他：图标必须纯色不透明（1024×1024，禁 Alpha）；首启不得出现「内测/测试/预览版」字样；**AI 生成内容需显式标识**（常驻灰字）；隐私弹窗链接必须可达；APP 备案主体/应用名/包名三者一致；`versionCode` 严格递增；应用名禁用 `Harmony` 等词；需提供可用测试 Key。
- 补丁链纪律：`git apply --reverse --check` 幂等判据；**新补丁不得落在既有补丁的连续上下文区间**（默认前后各 3 行）；新补丁追加到列表末尾；正反向往返须能 SHA-256 还原。
- ⚠️ **工具链差异会致命**：同源码/同 SO/同产物「他机编译不崩、本机编译崩」，差异锁定在 `ets/modules.abc` 与 `resources.index` → **本工程第一天就要对齐并固定 DevEco/hvigor/ArkTS 编译器版本**。

### 2.5 `oc-desktop-hos`（插件机制参考）

本工程参考其**插件机制的形态**（三档降级 + 壳专用插件落点 + 失败可见性纪律），但不照搬其对象模型：opencode 的插件与 pi 的扩展**宿主契约完全不同**（见 §5.1 对照）。其可复用的抽象是：

1. **三档降级**（全关 / 仅本地 / 允许安装）与「v1 默认仅本地」的取舍。
2. **壳专用插件必须落到运行时的配置目录**，只放进 `resfile` **不会生效**。
3. **禁止 symlink，一律 copy 物化**（应用域 `EACCES`）。
4. **失败可见**：`pending`/`failed` 状态必须在壳层有可见提示，**禁止静默失败**。
5. 每条候选补丁必须写明「触发条件 / 实施时机 / 替代方案」，占用全局唯一编号。

## 3. 目标与原则

**目标**

1. 在鸿蒙 2in1/平板设备上提供 `pi` 的**一等公民**桌面应用（对标「`pi` + 浏览器打开 `pi-web`」的桌面体验），而非「包一层浏览器指向 localhost」的粗壳。
2. **100% 复用 Pi Web UI**，不 fork 前端。
3. 核心链路（会话、对话、工具调用、文件读写、模型与凭据配置）端到端可用，**缺能力统一优雅降级且如实可见**。

**原则**

1. **零上游改动优先**：先穷尽上游现成机制（环境变量、注入点、配置），再考虑补丁。本版预计 0 条补丁即是这条原则的产物。
2. **主进程进程内宿主**：服务端跑在 Electron 主进程（Node 22.17），不引入子进程 —— 同时规避「exit 事件不触发」「每 spawn 泄漏 1 僵尸」「应用域子进程 JIT 被 seccomp 拦」三个平台问题。
3. **只写装配代码**：业务逻辑全在上游；本工程写环境装配、产物就位、建窗、生命周期、构建脚本。
4. **同源数据面**：渲染层只认 HTTP（同源），**零 CORS、零自定义协议、零 preload 桥、零 IPC 载体**（R1 与 R2 都不需要）。
5. **失败可见（fail-visible）**：每个启动阶段必须可观测；不允许「卡住但不说」，也不允许静默降级。
6. **补丁纪律**：若确需补丁，严格遵循 §2.4c 的幂等/上下文/往返规则，并写明触发条件。

### 4.2 服务端宿主形态：主进程进程内（已决策）

**为什么不用子进程**（三条平台级理由，🔶 沿用 dsh 真机结论）：

1. **子进程退出不可观测** → 无法判断服务端是否已死/需重启，也无法可靠清理。
2. **每 spawn 泄漏 1 僵尸** → 长驻服务端进程反复重启会累积。
3. **应用域 fork+exec 出的 node 脚本 SIGSYS**（JIT 可执行内存分配被 seccomp 拦）→ 用 Electron 二进制再 spawn 一个 Node 子进程**风险未知**（⬜ 需要的话另做探针）。

**进程内宿主的形态**（`src-main/main.js`）：

| 步骤 | 内容 |
|---|---|
| 1 | `ensureSandboxEnv()`：`HOME`/`USERPROFILE` → `app.getPath('userData')`；`PI_CODING_AGENT_DIR` → `<userData>/pi-agent`；`TMPDIR` → `<userData>/tmp`；`PI_OFFLINE=1`（PL1 默认，见 §5.3） |
| 2 | `ensurePiDistExtracted()`：`pi-dist.tar.gz` → `<userData>/pi-dist`（幂等，SHA-256 marker） |
| 3 | `rotatePreviewSecrets()`：复用 pi-web 的 `bin/rotate-preview-secrets.js`，**必须在起服务前**执行 |
| 4 | `resolveFreePort()`：取一个空闲高位端口（`server.listen(0)` 探测后释放） |
| 5 | `startServer()`：进程内启动 Next（`next/dist/bin/next` 的 `start` 语义，或用其导出的 server 入口），绑定 `0.0.0.0:<port>`，`PI_WEB_HOSTNAME=<局域网IP>` |
| 6 | `waitForReady()`：**HTTP 轮询** `GET /api/...`（**不监听 stdout 的 `Ready`**，那是子进程方案的做法） |
| 7 | `createWindow()` + `loadURL('http://<局域网IP>:<port>/')` |

⚠️ **实现要点（⬜ 待验证，Phase 0 的 P0-1 探针必过）**：`next/dist/bin/next` 是 **CLI 入口**（会 `process.exit()`、注册信号处理），在 Electron 主进程内**不能直接用**。两条候选：

- **候选 A（优选）**：直接调用 Next 的 server 入口（`next/dist/server/lib/start-server` 的导出），自行提供 `hostname`/`port`/`dir`，把生命周期握在自己手里。
- **候选 B（兜底）**：`child_process.spawn(process.execPath, [nextBin, "start", ...], { env: { ELECTRON_RUN_AS_NODE: "1" } })`，并把就绪判定改为 HTTP 轮询（不监听 stdout/exit）。**代价**：回到子进程方案的三条平台问题上。

→ **P0-1 出口判据**：候选 A 可用即定案；否则退候选 B 并登记风险。

**替换了 `bin/pi-web.js` 的三件事**（必须自己实现，不能依赖它）：`rotatePreviewSecrets`、`PI_WEB_HOSTNAME` 注入、run-record（`~/.pi/agent/pi-web-run/`；本工程**不写 run-record**，因为对应的是 CLI 启动的服务器）。另外 **`bin/node-version.js` 的 `>=22.19.0` 硬门禁因不经该入口而失效** —— 这是选择进程内宿主的一个附带收益。

### 4.3 渲染通道：R1（Chromium）为 v1，R2（ArkWeb）为触发式目标（已决策）

| 候选 | 说明 | 判断 |
|---|---|---|
| **R1 Electron BrowserWindow（Chromium）** | `loadURL('http://<局域网IP>:<port>/')`；鸿蒙侧由 `web_engine` 的 `XComponent(SURFACE) + nativeContext.runBrowser()` 承载原生 Chromium 渲染面 | ✅ **v1 选定**：与运行时架构一致、同型工程已跑通、pi Web UI 无 Node 依赖（纯浏览器代码） |
| **R2 ArkWeb（`@kit.ArkWeb` 的 `Web` 组件）** | ArkTS 侧加载同一地址，Electron 退化为只跑 Node 的主进程 | ⬜ **R2 为触发式目标**（触发条件见 §11.1 R1）：合规友好、**可能**顺带退役 loopback/绑定/局域网暴露问题；但需重接窗口/输入法/剪贴板/拖拽/托盘，工作量与不确定性大 |

**R1 的必备项**（⬜ Phase 0 验证）：

- **`loadURL` 必须用局域网 IP，不能用 `127.0.0.1`**（loopback 隔离）。
- **渲染层「先 loading 再加载真实 URL」**：首次启动要解压产物（数十秒量级），直接加载会长时间白屏。
- **`crypto.randomUUID` 可能缺失** → 需要的时候用 preload 兜底（dsh 的 `renderer-preload.js` 做了这项 + 一个 host 标识注入；本工程按 P0-3 探针结果决定是否需要）。
- **非安全上下文**：`http://<局域网IP>` 不满足安全上下文 → `crypto.subtle` / Service Worker / 通知可能受限。处置：`app.commandLine.appendSwitch("unsafely-treat-insecure-origin-as-secure", "http://<ip>:<port>")`（⬜ 待验证有效性）。
- **`window.open` 必须拦截**：pi Web UI 用 `window.open` 打开 OAuth 登录页与会话导出。v1 处置：`setWindowOpenHandler` 转到 ArkWeb 外链页（§4.7），不做弹窗。
- **PWA / Web Push 视为可选**：pi-web 在**生产模式**注册 `public/sw.js`，Web Push 依赖 `navigator.serviceWorker.ready`。v1 明示不承诺（不注册 SW，功能不依赖它）。

| 项 | 方案 | 状态 |
|---|---|---|
| 绑定地址 | `0.0.0.0` + 随机高位端口 | **必需**（loopback 隔离） |
| UI 访问 | `http://<局域网IP>:<port>/`（取非 internal 的 IPv4，回退 `127.0.0.1`） | **必需** |

### 4.6 沙箱与目录映射

真机沙箱事实（🔶 沿用，见 §2.4b）：`homedir()` = `/storage/Users/currentUser` **不可写**；`userData` = `/data/storage/el2/base/files`（hmfs，可写）；缓存 `/data/storage/el2/base/cache`；`/tmp` 与 `os.tmpdir()` 不可写且 `TMPDIR` 无效；symlink `EACCES`；`chmod` 静默失效。

| 变量 | 目标 | 理由 |
|---|---|---|
| `HOME` / `USERPROFILE` | `<userData>` | 让「家目录」可写（dsh 实测的 `EPERM` 修复） |
| **`PI_CODING_AGENT_DIR`** | **`<userData>/pi-agent`** | 承载 `settings.json`/`mcp.json`/`models.json`/`auth.json`/`extensions/`/`skills/`/`prompts/`/`themes/`/`agents/`/`trust.json`/`sessions/`/`npm/`/`git/` |
| `TMPDIR` | `<userData>/tmp`，并 **monkey-patch `os.tmpdir()`** | 真机上环境变量对 Node 无效 |
| `PI_OFFLINE` | `1`（PL1 默认） | 关闭「自动安装缺失包源」与「fd/rg 二进制下载」（§5.3） |
| `PI_WEB_HOSTNAME` | 局域网 IP | Host 白名单与 URL 生成 |
| `PI_WEB_PASSWORD` | 宿主生成的随机强密码 | 鉴权 |
| `NO_PROXY` / `no_proxy` | `127.0.0.1,localhost,<局域网IP>` | 避免代理拦截本机请求 |

补充规则：**优先用绝对路径调用外部命令**（`/system/bin/sh`、`/system/bin/toybox`），不要依赖 PATH 查找。

**关于内置数据目录的取舍**：`pi-web` 的 `files/` 路由受 `lib/file-access.ts` 的**允许根**约束（工作目录 + 应用已知的项目/会话根），不是通用文件浏览器。v1 的目录选择器默认落在 `<userData>/pi-agent` 与 `<userData>/pi-cwd`，外部目录由用户在系统设置授权后加入（🔶 沿用 dsh 的用户目录授权结论）。

### 4.8 进程模型与数据流

**进程模型（三层）**

| 层 | 进程 | 职责 |
|---|---|---|
| 运行时层 | Electron 主进程（Node 22.17.0） | 环境装配、产物解压、**Next 服务器 + agent**、建窗、生命周期 |
| 渲染层 | 渲染进程（Chromium） | 同源加载 Pi Web UI；`fetch /api/*` + SSE 订阅 |
| 桥接层 | ArkTS（`web_engine` HAR） | ArkUI 组件承载窗口 + `*AdapterBind` 桥接系统能力；ArkWeb 外链页 |

**数据流**

- **上行（unary）**：渲染进程 `fetch('/api/<route>')`（同源）→ Next 服务器 → pi-web 路由 → pi SDK。
- **下行（事件帧）**：渲染进程 `EventSource('/api/agent/[id]/events')` → `text/event-stream`。
- **无 IPC 载体**：桌面壳不向渲染层暴露任何 Node 能力（无 preload 桥的必要）；一切经 HTTP。

### 4.9 启动时序（失败可见）

```

   ├─ 失败 → loading 页显示具体阶段与原因（fail-visible，不静默降级）
   → [artifact] 产物就位（首次解压 pi-dist.tar.gz；marker 幂等）
   → [server] Next 服务器启动（进程内）+ rotatePreviewSecrets

   → [load] loadURL(http://<局域网IP>:<port>/) → 首屏完成 → 关闭 loading 页
```

规则：**每个阶段必须可观测**（统一日志前缀 `[pi-desktop]` + hilog 关键字 + loading 页阶段文本）；诊断落点沿用 dsh 纪律（`globalThis.__hostError` / `__extractError` / `__renderError`），并在真机用 `hdc shell hilog -x | grep pi-desktop` 取证。

## 5. 插件机制（已指定）

> 本节回答「本工程的插件机制是什么」。它同时是 `specs/201-plugin-runtime/` 的规划输入。

### 5.1 pi 侧事实：四个「插件/扩展」层面（✅ 源码核实）

| 层 | 形态 | 发现位置 | 需要子进程？ | 设备侧可行性 |
|---|---|---|---|---|
| **扩展** | TS/JS 模块，`export default function (pi: ExtensionAPI) {}`；jiti 加载、**无需编译**；`package.json` 的 `pi.extensions[]` → `index.ts` → `index.js` 依次探测；目录扫描覆盖直接 `*.ts` / `*.js` 与**仅一层**子目录 | `<cwd>/.pi/extensions/` → `<agent-dir>/extensions/` → `settings.extensions[]` → CLI `-e/--extension`（按解析后绝对路径去重） | 否 | ✅ 原生可用 |
| **Pi packages** | 四类源：`npm:` / `git:` / URL / **本地路径**；`package.json` 的 `pi: {extensions,skills,prompts,themes}` 显式清单，或 `extensions/ skills/ prompts/ themes/` 约定目录；keyword `pi-package` | 声明在 `settings.packages[]`（对象形式可加过滤） | **仅 npm/git 两类需要** | ⚠️ **仅本地路径类可用** |
| **内置扩展** | `codemode` / `tool-search` / `mcp` 三工厂；pi-web 以 `{name, factory, replaceable: true, builtin: true}` 注入 `extensionFactories`；路径名 `builtin:<name>` | 由宿主注入（不经文件发现） | codemode 需 `worker_threads` + QuickJS wasm | ⚠️ 需真机探测（§11.2 O1） |
| **MCP 服务器** | `mcp.json` 的 `mcpServers{}`；stdio（`command`/`args`/`env`/`cwd`）或 streamable HTTP（`url`/`headers`/`oauth`） | `<agent-dir>/mcp.json` + `.pi/mcp.json`（后者需 project trust） | **stdio 类需要** | ⚠️ HTTP 可用；stdio 受限 |

**其他扩展面（全部纯文件系统）**：技能 `<agent-dir>/skills/`、提示模板 `<agent-dir>/prompts/`、主题 `<agent-dir>/themes/`、子 agent 配置 `<agent-dir>/agents/*.md` + `<agent-dir>/agents/settings.json`。

**资源优先级**（✅ 源码核实，`package-manager.ts` 的 `resourcePrecedenceRank`）：项目本地(0) → 项目 package(1) → 用户本地(2) → 用户 package(3，`origin === "package"` 统一为 4) → **内置(5)**。即 **内置扩展最后加载，可被本地与包覆盖** —— 这正是「用户可改写内置行为」的来源，不要"修掉"它。

**扩展的权限模型（必须如实记录）**：扩展**在 pi 进程内运行，拥有与进程相同的操作系统权限**（可读提示、工具调用、文件、凭据、会话历史）。**唯一的门禁是 project trust**（`defaultProjectTrust` 默认 `"ask"`）。→ 这是本工程把「仅本地源」作为默认档的根据。

**三个关键注入点（✅ 源码核实，本工程 PL1 的实现基础）**

1. `DefaultPackageManager.resolve(onMissing?: (source) => Promise<"install" | "skip" | "error">)` —— **公开注入点**。`resolvePackageSources()` 内：传了 `onMissing` 就**不调用 `installParsedSource()`**（只按返回值决定 `install` / `skip` / `error`）。pi-web 的 `/api/plugins` 与 built-in 开关解析**已经**传 `() => "skip"`。
2. `PI_OFFLINE` —— **总闸**。包管理器 `installMissing()` 首行 `if (isOfflineModeEnabled()) return false`；同一旗标也让 `fd`/`rg` 的**自动下载**变成一条 warning 后返回 `undefined`（不写盘、不报错）。
3. **本地路径类源**走 `resolveLocalExtensionSource()`，**完全不碰 npm/git**。

**需要子进程的确切位置（按设备侧顺序）**

| 位置 | 命令 | 设备侧 |
|---|---|---|
| `package-manager.ts` `spawnCommand` | `npm install <spec> --prefix <agent-dir>/npm …`、`npm uninstall …`、`npm view <spec> version --json`、`npm root -g` | ❌ 无 npm |
| `package-manager.ts` `runCommand("git", …)` | `git clone` / `git fetch` / `git rev-parse` | ❌ 无 git |
| `pi-web/lib/npx.ts` | `node <npm-cli.js> …` / `npx-cli.js`（技能安装、插件更新检查） | ❌ 无 npm/npx |
| `pi-web/lib/plugin-updates.ts`、`lib/skill-updates.ts` | `npm view`、`git init --bare`/`git ls-remote` | ❌ |
| `pi-web/lib/git-changes.ts`、`lib/worktree.ts`、`lib/file-tree-visibility.ts`、`app/api/file-index/route.ts` | `git -C … status/diff`、`git worktree`、`git check-ignore` | ❌（见 §9.3 降级） |
| `pi-web/lib/terminal-manager.ts` | `node-pty`（原生模块） | ❌（无 ohos 产物） |

### 5.2 目标模型：三档（对齐 `oc-desktop-hos` 的抽象，换成 pi 的机制）

| 档 | 含义 | 落地动作 | v1 |
|---|---|---|---|
| **PL0 全关** | 插件通道静默 | `settings.json`：`extensions: ["-builtin:codemode","-builtin:tool-search","-builtin:mcp"]` + 不投放任何扩展/技能目录 | 不用 |
| **PL1 仅本地源** | 只加载**随壳投放**与**本地路径**声明的扩展/技能；**绝不自动安装、绝不联网取包** | ① `settings.packages[]` 只写本地相对/绝对路径；② **`PI_OFFLINE=1`**；③ 网络源（`npm:`/`git:`/URL）在 UI 上**明示不可用** | ✅ **默认** |
| **PL2 允许安装** | 设备侧可联网安装 npm/git 源 | 解禁 `PI_OFFLINE` + 宿主已具备 npm/git（🔶 dsh 的「路线一：依赖主机自带工具链」：应用 PATH 已含 `/data/service/hnp/bin`，只缺 `pnpm`） | 二期，须先过 O2 |

**PL1 为什么是「零补丁」档**：三个拦截点全是上游现成机制（§5.1 的三个注入点）。**本工程 v1 不需要写任何插件闸门补丁**，也不需要在设备上装 npm/git。

### 5.3 v1 落地契约

**a) 预置文件：`config/` 模板 → 首次启动写到 `<userData>/pi-agent/`（幂等，已存在则不覆盖）**

```
<userData>/pi-agent/
├── settings.json        # 壳预置：packages 只含本地源（可空）；defaultProjectTrust 显式写 "ask"
├── mcp.json             # 空壳 { "mcpServers": {} }
├── extensions/          # 壳专用扩展（随壳分发，启动时 copy 物化）
├── skills/              # 壳专用技能（随壳分发，启动时 copy 物化）
├── packages/            # 壳专用本地 package（可选；settings.packages 写相对路径）
├── agents/              # 壳预置子 agent 配置（可选）
└── trust.json           # 由 pi 自己管理，本工程不预写
```

**b) 三条硬规则**

1. **禁用 symlink，一律 copy 物化**（🔶 应用域 `EACCES`）。这同时意味着「壳专用技能随壳更新」需要一条 copy 与覆盖判定，而不是链上去。
2. **壳预置内容不覆盖用户改动**：`settings.json` / `mcp.json` 只在**不存在**时写入；`extensions/`、`skills/` 的壳内容按「同名则以壳为准 or 以用户为准」需要一次显式决定 —— 本工程选择 **`skills/` 以用户为准（不覆盖同名），`extensions/` 以壳为准（覆盖壳自己的同名项）**，理由是技能是模型可见的标识符，用户的同名覆盖是有意行为（对齐 dsh 的「用户可改写内置行为」结论）；而扩展是代码，版本漂移比覆盖更危险。
3. **只落运行时配置目录**：`resfile` 内的 `pi-dist/resources/pi-agent/{extensions,skills,...}` 是**投放源**，**不是生效位置**。仅放进 `resfile` 不会生效（对齐 oc 的同款结论）。

**c) 环境变量（PL1）**

| 变量 | 值 | 作用 |
|---|---|---|
| `PI_OFFLINE` | `1` | 关闭包自动安装 + fd/rg 自动下载（两者都变成可见 warning，不是硬失败） |
| `PI_CODING_AGENT_DIR` | `<userData>/pi-agent` | 数据与扩展根 |

### 5.4 壳专用扩展 / 技能 / 子 agent 的落点

| 内容 | 落点 | 发现机制 |
|---|---|---|
| 壳专用**扩展** | `<userData>/pi-agent/extensions/` | ✅ 自动扫描（直接 `*.ts` / `*.js` + 一层子目录） |
| 壳专用**本地 package** | `<userData>/pi-agent/packages/<name>/` + `settings.packages` 写相对路径 | 相对路径**相对声明它的 settings 文件**解析 |
| 壳专用**技能** | `<userData>/pi-agent/skills/` | ✅ `skills` 发现集（另有 `~/.agents/skills`、`.agents/skills` 兼容目录） |
| 壳预置**子 agent** | `<userData>/pi-agent/agents/*.md` | ✅ 优先级 builtin < global < workspace < project |
| **能力边界技能** | `skills/harmony-runtime-capabilities/SKILL.md`（源码）→ copy 到上表位置 | 技能描述的是**本构建的能力边界**；⚠️ **能力变化时必须同步更新引用该能力的技能**（🔶 dsh 的教训：过期技能比没有技能更有害） |

### 5.5 必须在壳层显式处置的三点（否则就是静默失败）

| # | 事实 | 处置 |
|---|---|---|
| 1 | **`PI_WEB_DISABLE_MCP` 是全局开/关**，做不到「只禁 stdio」。而 stdio MCP 服务器是「📌 每 spawn 泄漏 1 僵尸 + exit 事件不可观测」。MCP 扩展是 pi-web 自己的（**不依赖 pi 二进制**） | v1：**MCP 面板保留可见**；**stdio 类条目在 UI 上明示「本设备不支持本地子进程服务器」**；HTTP / streamable 类正常可用。⬜ O3 探测后定稿 |
| 2 | **pi-web「Plugins」面板的 install 走 `installAndPersist` → npm/git spawn**（`app/api/plugins/route.ts`） | PL1 下这条动作必须**拒绝并给出明确原因**（不是静默转圈）。⬜ 实现位置待定：优先在宿主侧对 `/api/plugins` 的写动作做**响应改写**，避免上游补丁 |
| 3 | **`defaultProjectTrust` 默认 `"ask"`**（✅ `project-trust.ts:77`）—— `.pi/extensions`、`.pi/mcp.json` 默认不加载 | **保持默认，绝不改成 `always`**。这对本工程是**有利的**：项目级资源天然需要用户显式信任 |

### 5.6 失败可见性（纪律）

- **L2/PL2 未启用时，`/api/plugins` 的 `pending` / `failed` 状态必须在壳层有可见提示**，禁止静默失败（对齐 oc 的同款纪律）。PL1 下「网络源不可用」属**预期行为**，不是故障 —— UI 文案与验收脚本都不得把它当错误。
- 技能与扩展的**加载失败**必须可见（pi 的扩展错误会汇报；壳层要在 UI 暴露，至少落到 `[pi-desktop]` 日志 + hilog）。

## 7. 补丁集

**本版为 0 条必需补丁。** 这是一个**结论**而不是省略，理由逐条登记：

| 潜在补丁 | 是否需要 | 理由 |
|---|---|---|
| Node 版本门禁（`>=22.19.0`） | ❌ | 该门禁位于 `bin/pi-web.js`，而本工程**不经该入口**（§4.2 进程内宿主） |
| 插件/包安装闸门 | ❌ | PL1 由 `PI_OFFLINE` + 本地路径源 + `onMissing` 三点覆盖（§5.1） |
| `node:sqlite` 不可用 | ❌ | `pi` 的 SQLite 在 `packages/durable`（本工程不用）；pi-web 用 JSONL 会话文件 |
| zstd / 新 Node API | ❌ | `pi` 侧普遍有运行守卫（✅ 例：`zlib.zstdCompressSync` 的 `typeof` 判空） |
| 原生模块（PTY / sharp / koffi） | ❌ | 本工程**不随包分发原生模块**；终端降级（§10） |
| 网络绑定 / 头改写 | ❌ | pi-web 的 Host 白名单放行 IP 字面量（§4.5） |
| symlink / hardlink / chmod | ❌ | pi-web 与 pi 的写入路径未依赖它们；⬜ 若实测命中，按 §2.4b 的结论补一条回退补丁 |

**`patches/` 目录与 README 仍然建立**，写明「本版本为空」及其理由 —— 附带条件：一旦某条潜在补丁真的需要，必须同时登记「触发条件 / 实施时机 / 替代方案」并占用全局唯一编号（对齐 oc 的候选补丁登记规则）。

**若确需补丁，遵守**（🔶 沿用）：

1. **幂等**：应用前先 `git apply --reverse --check`，成功即视为已应用 → 跳过。
2. **冲突即终止**：绝不 `--3way` 强行合并，绝不覆盖 `../pi` 或 `../pi-web` 中的用户改动。
3. **不带镜像噪声**：`package-lock.json` 等由 `npm install` 重新生成，不进补丁。
4. **按上游 tag 组织**：`patches/v0.11.1/`；上游升级时新增目录，旧目录保留可追溯。
5. **不得落在既有补丁的连续上下文区间**（前后各 3 行），新补丁一律追加到列表末尾。
6. **可往返**：正向应用 → 反向应用后源码 SHA-256 必须还原。
7. 补丁只在**独立的 detached worktree** 中生成与校验。

### 8.4 开发/调试循环

- **host 侧调试（摆脱真机往返）**：用与设备同版本的 Node（22.17.0）直接跑 `../pi-web` 的 `next start`，在浏览器里验证服务端与 UI。

## 9. 能力范围与降级

### 9.1 v1 In scope（必须达成）

1. HAP 可安装启动，进入 **Pi Desktop** 窗口，无白屏、无闪退。
2. pi-web 服务端在宿主内就绪；`GET /` 返回 SPA；`GET /api/...` 通过。
3. **Web UI 全功能可用**：会话列表/新建/重命名/导出、发消息、流式响应（SSE）、工具调用可视化、审批交互、上下文用量/成本、主题、多语言。
4. **会话持久化**：重启应用后会话仍在（JSONL → `<userData>/pi-agent/sessions/`）。
5. **模型与凭据配置**：Settings › Models 可登录 / 填 API Key；`auth.json` 落沙箱。
6. **工作目录选择与授权**：用户能在应用内选定工作目录。
7. **文件类工具可用**：读取 / 写入 / 编辑 / 列目录 / 图片附件（走平台或纯 JS 能力）。
8. **插件机制 PL1 生效**：壳专用扩展与技能随壳可加载；网络源明示不可用。
9. **合规低成本项落地**：无浏览器语义 + 外链 ArkWeb 化。
10. **构建可复现**：一条命令链从零产出签名 HAP，且 host 侧 Node 22.17 门禁全绿。

### 9.2 v1 Out of scope（二期+）

| 项 | 原因 | 计划 |
|---|---|---|
| 终端面板 / PTY | **平台级不可用**（SELinux 拒 `forkpty`/`openpty`/`popen`）+ `node-pty` 无 ohos 产物 | 不作为规划项 |
| `git` 集成 / VCS / worktree | 设备无 `git`（toybox 不提供） | Phase 2 评估 isomorphic-git 类纯 JS 方案 |
| 内容搜索（`rg`）/ `fd` | pi 会下载 GitHub release 二进制到 `<agent-dir>/bin`；设备无 `rg`/`fd` 且下载物是 glibc aarch64 ELF | v1 优雅降级（明示）；Phase 2 评估纯 JS 走查 |
| 插件网络安装（PL2） | 设备无 npm/git；安装 = 联网 + 落盘 + 进程内执行第三方 JS | Phase 2，须先过 O2 |
| MCP stdio 服务器 | 需 spawn 子进程（僵尸泄漏 + exit 事件不可观测） | v1 明示不可用；HTTP/streamable 可用 |
| OAuth 回环登录 | 部分 provider 的 OAuth 回调需要 `127.0.0.1` 回环，与 loopback 隔离冲突 | v1 引导 API Key；Phase 2 评估 |
| 系统托盘 / 深链 / 系统通知 | 2in1 无传统托盘语义；`statusBarView` 需另接 | Phase 2/3（🔶 状态栏 API 已就绪且无需权限，dsh 已交付） |
| 开机自启 | **无公开 setter**（`autoStartupManager` 只有只读接口） | 不实现；只能引导用户在系统设置中手动开启 |
| 自动更新 | 无静默自更新的公开 API | 不实现 |
| 主 UI 的 ArkWeb 迁移（R2） | 工作量与不确定性大 | 触发式目标（§11.1 R1） |

### 9.3 鸿蒙能力缺口与降级表

| 缺口 | 根因层 | v1 降级 |

### 11.4 权限与签名

**必须申请（ACL，受限权限）**：判定规则（🔶 沿用 dsh 的权威口径）—— **受限权限 ⟺ `provisionEnable == true` 且 `availableLevel ∈ {system_basic, system_core}`**。仅凭名称含 `kernel.` 就主张申请是错的。

| 权限 | level / since | 用途 |
|---|---|---|
| `ohos.permission.kernel.ALLOW_WRITABLE_CODE_MEMORY` | `system_basic` / since API 14 / 仅平板 + 2in1 / **受限** | 启用 Electron/V8 **JIT**，引擎必需，**不可删除**；须同时出现在 `web_engine` 的 `requestPermissions` 与 `definePermissions` |

**开放权限（免 ACL，写进 `requestPermissions` 即安装时授予）**：`INTERNET`、`GET_NETWORK_INFO`、`KEEP_BACKGROUND_RUNNING`（配合 `backgroundModes: ["taskKeeping"]`）、`READ_WRITE_DOCUMENTS_DIRECTORY`、`READ_WRITE_DOWNLOAD_DIRECTORY`、`FILE_ACCESS_PERSIST`。

**本工程不需要申请**：二进制证书（AGC `certType: 4`，不随包分发自有 ELF）、`ALLOW_EXTERNAL_NATIVE_CODE`、`kernel.LOAD_INDEPENDENT_LIBRARY`、`READ_WRITE_DESKTOP_DIRECTORY`（`system_basic`，上架障碍）、`CUSTOM_SANDBOX` / `RUN_ANY_CODE` / `ACCESS_USER_FULL_DISK`。

**签名**：不能用 `com.huawei.ohos_electron` 的共享签名，必须用 DevEco 为本 bundleName **重新生成证书**；签名材料**外置且 gitignored**（`signing.{debug,release}.local.json`，由 `hvigorfile.ts` 在 `afterNodeEvaluate` **仅内存注入**，`build-profile.json5` 以 `"signingConfigs": []` 入库）。**自定义包名意味着 ACL 需为本包名重新申请。** ⚠️ **发布签名的包无法侧载**（`hdc app install` 报 `signature verification failed due to not trusted app source`）—— 真机回归请用「release 编译 + debug 签名」。

**ACL 提交要点**（🔶 沿用）：AGC → 项目设置 → **ACL 权限**页签 → 选择权限并填申请原因（≤256 字）与使用场景 → 审核约 3 个工作日；**单次最多 30 项，上一批未审完不能提交新批次**；获批权限在**创建发布 Profile 时写入**，若 Profile 创建后 ACL 变化**必须重建 Profile**；可用**试用调试 Profile**（5 天、每应用最多 5 个）先做可行性验证。
